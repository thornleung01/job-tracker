### 3.3 What could not be checked

- No real Google or Microsoft login, and no real mailbox. The first real one-click Google login after this work is the final proof of that flow.
- Whether Google's identity script ever returns a different mailbox's token on a silent refresh ([SEC-WEB-3](reports/security-web.md#sec-web-3-a-silent-token-refresh-is-never-checked-against-the-mailbox-it-was-connected-for-the-connected-address-map-survives-sign-out)), and whether Gmail or Exchange deliver a sender address with quote characters unchanged ([SEC-PY-1](reports/security-python.md#sec-py-1-javascript-string-injection-stored-xss-from-an-emails-sender-address-in-the-reply-confirm-dialog)). The app side of both was reproduced; the provider side is an assumption.
- No screen reader, no 400% zoom, no forced-colors run beyond the sign-in page. Accessibility findings come from code reading plus the Chrome checks in [validation-ui-perf.md](validation/validation-ui-perf.md).
- Windows-only code (DPAPI token files, toast pop-ups, `scripts/install-task.ps1`) was read, not run. Everything was run on macOS with Python 3.14.4 only. The suggested CI job for Windows has not been run on Windows.
- Gmail and Outlook latency, so the download-speed claims in [PERF-2](reports/performance.md#perf-2-gmail-messages-are-downloaded-one-at-a-time-estimate) and [PERF-7](reports/performance.md#perf-7-outlook-downloads-the-body-of-every-message-again-on-rescans) are estimates. Performance data used synthetic mail, so absolute numbers will differ on a real mailbox.
- The exact wording of Google Cloud and Microsoft Entra console screens cannot be checked offline. [documentation.md](reports/documentation.md#console-wording-that-i-could-not-verify-offline) lists seven groups of console wording to confirm by hand.
- The sign-in screen part of [BP-UI-6](reports/bestpractices-web-ui.md#bp-ui-6-appearance-is-applied-after-first-paint-and---accent-l----accent-d-are-not-defined-in-any-stylesheet) (the committed site config has no client ids, so the signed-in build cannot be run locally).
- One extra check by the coordinator: `curl` against `https://oauth2.googleapis.com/tokeninfo` with `Origin: https://thornleung01.github.io` returns `access-control-allow-origin` for POST, GET and the OPTIONS preflight. So the token check in the new one-click Google login should work from the live site. It was only tried with a bogus token. See also [TQ-7](reports/testquality.md#tq-7-the-cross-origin-contracts-tokeninfo-job-board-apis-are-only-verified-by-hand-with-no-canary), which found the same for the job-board APIs.

### 5.1 Data correctness

#### [BP-LOGIC-4](reports/bestpractices-web-logic.md#bp-logic-4-calendar-day-is-validated-in-local-time-but-displayed-and-exported-from-the-utc-prefix) (with [BP-LOGIC-5](reports/bestpractices-web-logic.md#bp-logic-5-two-day-stamp-implementations-that-diverge-whenfor-vs-appliedstamp)): evening mail shows the wrong day. Medium, the most user-visible bug

- **What is wrong.** The app checks days in local time but shows and exports them from the UTC date. An email that arrives at 9 pm in Toronto on 21 October is stamped 22 October (UTC). The list, the detail page and the CSV say Oct 22, while the time label on the same email says Oct 21, 9:00 pm. An evening CSV export is named for tomorrow. The quick date editor opens on Oct 21 and will not let you re-enter the Oct 22 the list shows.
- **Where.** `web/src/sync/actions.ts:52-58` (`appliedStamp`), `web/src/components/TimeText.tsx:64-72` (`dayText`), `web/src/portability/csv.ts:30,43`, `web/src/components/quickedit/QuickDate.tsx:28-33`, `web/src/sync/activity.ts:49-57` (`whenFor`, the second copy of the stamp logic).
- **Shown by.** Real functions run under `TZ=America/Toronto` ([skeptic check](validation/validation-web-logic.md#bp-logic-4--confirmed-more-common-than-the-report-says)). A sweep of 192 manual date picks per zone was wrong 0 times in Toronto but 44 times in Sydney and 56 in Kiritimati (UTC-plus zones, early local hours).
- **Who is affected.** Every application created from email for anyone west of UTC, for mail after about 8 pm EDT or 7 pm EST (4 to 5 hours a day). Manual picks are only wrong in UTC-plus zones. Stored data is right; the display and export are a day off. The suite is green in three timezones because no test covers an evening email in a UTC-minus zone.
- **Minimal fix.** One `localDay(iso)` helper in `db/time.ts`, used by `dayText` (for instants), the CSV `day()`, `csvFilename` and `QuickDate`. Store a manually chosen day always as `${day}T12:00:00Z`. Use one shared stamp function in place of `whenFor` and `appliedStamp` ([BP-LOGIC-5](reports/bestpractices-web-logic.md#bp-logic-5-two-day-stamp-implementations-that-diverge-whenfor-vs-appliedstamp) is the same fix and has no visible symptom today). Care is needed for rows already stored as instants versus noon-UTC day stamps. **Effort M.**
- **Related, unvalidated.** [BP-PY-10](reports/bestpractices-python.md#bp-py-10-date-applied-check-in-post-appadd-disagrees-with-the-local-day-logic-used-elsewhere-rejects-today-for-utc-users) (u): the Python "date applied" check has the same class of mismatch (it rejects "today" for UTC-plus users).

#### [BP-LOGIC-8](reports/bestpractices-web-logic.md#bp-logic-8-graph-folder-exclusion-lookups-ignore-failures-so-junksent-mail-can-be-read-as-job-mail): a failed Outlook folder lookup lets Junk and Sent mail in. Medium

- **What is wrong.** The sync looks up the Junk, Sent, Drafts and Deleted folders so it can skip them. If a lookup fails with 403, or with 429 or 5xx that outlasts the retries (about 170 seconds), the failure is ignored. The sync then reads those folders as job mail, shows no error, and moves the "last sync" date forward. Because those message ids are marked seen, the wrong rows stay until the user cleans them up.
- **Where.** `web/src/providers/graph.ts:76-80`.
- **Shown by.** A fake Graph server where the `junkemail` lookup returns 403, 429 or 503 and the Junk folder holds "Thank you for applying to Beta Corp": a "Beta Corp" application appears and `lastError` stays null ([skeptic check](validation/validation-web-logic.md#bp-logic-8--confirmed)). A 404 is intentional and tested.
- **Who.** Outlook users, rarely. The harm is wrong data with no signal, the reverse of the "mail skipped" the reviewer described.
- **Minimal fix.** Treat 404 as "no such folder"; for any other non-OK answer use `readJson`, which throws, so `syncAccount` records the error and does not advance the date. **Effort S.**

#### [BP-LOGIC-6](reports/bestpractices-web-logic.md#bp-logic-6-the-matching-algorithm-exists-twice-and-the-parity-tested-copy-is-not-the-one-the-app-runs): the matching code exists twice. Low, latent

- **What is wrong.** `web/src/pipeline/match.ts` is the copy checked against Python golden data. The app actually runs `web/src/sync/match.ts` (`sync/decide.ts:8,86`). The same applies to `Learned.blocks`. See also [CL-WEB-2](reports/clarity-web.md#cl-web-2-two-copies-of-the-matching-rules-two-copies-of-learned-two-free-mail-lists) (u) (unvalidated).
- **Shown by.** A differential test over a fake database: 400 golden cases and 5,000 random cases, 0 differences between the two copies ([skeptic check](validation/validation-web-logic.md#bp-logic-6--partly-confirmed)). So there is no bug today; the risk is that a future Python rule change is verified only in the copy the app does not run.
- **Minimal fix.** Decision (b) in section 9. Cheapest guard: a 20-line parity test that runs the golden `findApplication` inputs through `sync/match.ts` over a fake Dexie database. Full fix: make `sync/match.ts` do only the database reads and call `matchApplication`. **Effort S for the test, M for the rewire.**

#### [BP-LOGIC-3](reports/bestpractices-web-logic.md#bp-logic-3-read-then-write-outside-the-transaction-while-the-module-header-claims-each-action-is-one-transaction): "each action is one transaction" is not true. Low to Medium

- **What is wrong.** The header at `web/src/sync/actions.ts:1` is wrong for seven single-row actions, but those are harmless (an update to a missing row is a silent no-op). Two cases are real: `mergeApplications` (`actions.ts:150-178`) reads both rows before its transaction, and `recheck` (`web/src/sync/recheck.ts:30-75`) checks "untouched" outside its transaction. A second browser tab can slip in between.
- **Shown by.** Hooked reads that let a second writer run in the gap: a fresher `lastActivity` was overwritten; a merge target deleted in the gap left emails pointing at a dead id; a note added during `recheck` was deleted with its application ([skeptic check](validation/validation-web-logic.md#bp-logic-3--partly-confirmed)).
- **Who.** Needs two tabs or a sync landing within milliseconds; realistic risk is low.
- **Minimal fix.** Move the reads and the field computation inside the transaction in `mergeApplications`; re-run `untouched()` inside the transaction in `recheck`; reword the header; give `unlockStage` the same missing-record check. **Effort S.**

#### [SEC-PY-1](reports/security-python.md#sec-py-1-javascript-string-injection-stored-xss-from-an-emails-sender-address-in-the-reply-confirm-dialog) (same bug as [BP-PY-3](reports/bestpractices-python.md#bp-py-3-jinja-values-interpolated-into-inline-javascript-string-literals-onsubmitreturn-confirm-x-) and [SEC-PY-4](reports/security-python.md#sec-py-4-same-inline-js-pattern-with-contact-names-cannot-execute-code-today-but-breaks-the-confirm-and-is-one-regex-change-from-exploitable) (u)): script injection in the reply confirm box. Medium

- **What is wrong.** The reply form builds its "Are you sure?" box as `onsubmit="return confirm('Send this reply to {{ r_to }}?')"`. The sender's address goes straight into a JavaScript string. HTML escaping turns `'` into `&#39;`, but the browser decodes that back before running the script, so a quote ends the string and the rest runs.
- **Where.** `jobtracker/templates/_reply.html:5-7`; the contact-name twin at `jobtracker/templates/_person.html:27` ([SEC-PY-4](reports/security-python.md#sec-py-4-same-inline-js-pattern-with-contact-names-cannot-execute-code-today-but-breaks-the-confirm-and-is-one-regex-change-from-exploitable) (u)).
- **Shown by.** The real templates rendered with a hostile sender stored exactly as `sync.py` stores it, then the browser-decoded handler run in Node: the injected `fetch` fired ([skeptic check](validation/validation-security-python.md#sec-py-1-js-string-injection-via-sender-address-in-_replyhtml-onsubmit)). It is worse than reported: no parentheses are needed (a backtick template call works). The example in [BP-PY-3](reports/bestpractices-python.md#bp-py-3-jinja-values-interpolated-into-inline-javascript-string-literals-onsubmitreturn-confirm-x-) only works on the Outlook path, because Gmail address parsing mangles it.
- **Who.** Only a user who has switched on "Allow replying" (off by default), then opens an attacker's email that was classified as job mail, writes a reply and presses Send. Once it fires, the script can read every page, send data out, and even use the app's own reply endpoint. There is no Content-Security-Policy on this server.
- **Minimal fix.** Use `data-confirm="Send this reply to {{ r_to }}?"` plus one delegated `submit` listener in `base.html` (fixes [SEC-PY-4](reports/security-python.md#sec-py-4-same-inline-js-pattern-with-contact-names-cannot-execute-code-today-but-breaks-the-confirm-and-is-one-regex-change-from-exploitable) (u) too). If the inline handler must stay: `confirm({{ (...)|tojson|forceescape }})`; `tojson` alone is not enough. **Effort S.** Add a test with a hostile sender.
- **Not verified.** Whether Gmail or Exchange deliver such an address unchanged.

#### [SEC-WEB-1](reports/security-web.md#sec-web-1-mail-data-db-and-the-oauth-client-are-shared-with-every-page-on-the-thornleung01githubio-origin): the hosted app shares its web origin with every other page on `thornleung01.github.io`. Medium

- **What is wrong.** Browser storage and Google's "authorized origin" setting are bound to the site address, not the folder. The app lives at `https://thornleung01.github.io/job-tracker/`. Any other page published from the same account can read and change the app's stored email excerpts, notes and applications (nothing is encrypted at rest). For someone who already agreed to Gmail access, it could also request a mail token for the app's public client id (documented Google behaviour, not tried here).
- **Where.** `web/vite.config.ts:6` (`base`), `web/src/auth/user.ts:21-23` (database name), `web/src/pages/setup/steps.ts:4,15` (origin the setup guide asks you to register), `web/src/auth/google.ts:157-165`.
- **Shown by.** `gh api` on the account: two other Pages sites exist today, `balloons-by-tea` (a dynamic site with an admin page, analytics and a third-party script from a CDN) and `job-tracker-info` ([skeptic check](validation/validation-security-python.md#sec-web-1-hosted-app-shares-the-githubio-origin-with-other-pages-sites)). - **What it cannot do.** Read the in-memory tokens, get Microsoft tokens (exact-path redirect), or replace the app's own script. A Content-Security-Policy cannot help here.
- **Minimal fix.** Decision (a): give the app its own origin (custom domain: add `web/public/CNAME`, DNS, then update the Google authorized origin and the Microsoft redirect URI). Interim: move the other Pages sites off this account, or at least say in the README that the account must host nothing else. **Effort M, owner action.**

#### [SEC-WEB-2](reports/security-web.md#sec-web-2-privacy-page-says-other-site-links-cause-no-request-but-the-code-queries-greenhouse-for-any-site-with-gh_jid): the privacy page says something the code does not do. Low

### 5.4 Performance

#### [PERF-1](reports/performance.md#perf-1-every-sync-write-re-runs-three-or-more-full-table-emailstoarray-livequeries-so-sync-runs-about-60-to-90-times-slower-and-the-ui-thread-is-saturated): every sync write re-runs full-table live queries. High for a large stored mailbox, Medium for a normal first sync

- **What is wrong.** Each saved message commits a transaction, and each commit makes every live query that read `emails` run again. Two of those queries are always on screen: the review-count badge in the header (`web/src/app/Shell.tsx:26-28`) and the sync banner (`web/src/components/SyncBanner.tsx:100`). Both read the whole table. The next write waits for them, so sync time is dominated by re-reading.
- **Where.** `web/src/app/useQuery.ts:12`, `web/src/sync/queries.ts:180-182,222-226`, `web/src/db/schema.ts:174-176`, `web/src/sync/sync.ts:42,48`.
- **Shown by (numbers).**

| Stored emails | No live queries | With the two always-on queries | Slowdown | Source |
|---|---|---|---|---|
| 20,000 (1,000 apps) | 1.8 ms per message | 101.7 ms per message | 56x | skeptic ([skeptic check](validation/validation-ui-perf.md#perf-1-confirmed-high-for-large-stored-mailboxes-medium-for-a-normal-first-sync)) |
| 2,000 (200 apps) | 1.0 ms | 9.4 ms | 9x | skeptic |
| 20,000, realistic mix, 300 messages | 1.50 ms | 92.1 ms (137 ms with the Applications page query too) | 60 to 90x | reviewer |

The two sources agree on order of magnitude. At 2,000 rows a 1,500-message first sync takes about 12 seconds instead of 1.5; at 20,000 rows it is the 60 to 90x case. With the fix tested by the skeptic (re-runs at most once per second while a sync runs), cost fell back to 1.8 ms per message and the final badge and counts were correct.
- **Who.** Anyone with a large stored mailbox, a long lookback, or a rescan.
- **Minimal fix.** A trailing throttle of about one second, only for those two readers (`ReviewCount`, `SyncBanner`) and only while `isSyncing()`. Gating every `useQuery` would delay user edits during a sync by up to a second. **Effort S.** Optional later: batch 25 messages per transaction (M).

#### [PERF-2](reports/performance.md#perf-2-gmail-messages-are-downloaded-one-at-a-time-estimate): Gmail messages are downloaded one at a time. Medium to High, timings are estimates

- **What is wrong.** `web/src/providers/gmail.ts:119-132` fetches each message in turn. The reviewer's estimate is 4 to 8 minutes for 1,500 messages; this was not timed.
- **Minimal fix.** A window of 4 to 6 requests (not more: Gmail has a per-user concurrency limit), results yielded in order, a shared cool-down after a 429, the abort signal passed to every request, and the first non-404 error still stops the generator so partial batches are saved. Token refresh is already safe under concurrency. **Effort M**, risk Medium.

#### [PERF-3](reports/performance.md#perf-3-outlook-first-sync-and-rescans-hold-the-whole-mailbox-in-memory-including-an-html-copy-nobody-reads-memory-is-an-estimate): Outlook first sync holds the whole mailbox in memory. Medium (reviewer said High)

- **What is wrong.** Outlook is not read in batches (`web/src/pages/settings/actions.ts:111`, `web/src/sync/sync.ts:203-205`), and each message keeps an HTML copy that nothing reads (`providers/graph.ts:47,61`, `gmail.ts:77,88`).
- **Shown by.** Heap measurement with 2,000 synthetic 40 KB messages: 56.8 KB per message with the HTML, 16.7 KB without ([skeptic check](validation/validation-ui-perf.md#perf-3-confirmed-mechanism-memory-figure-overstated-about-2x-medium)). The reviewer's "about 100 KB per message, 500 MB for 5,000" was about twice too high; 5,000 messages is about 285 MB. The default 30-day window is fine.
- **Minimal fix, in order.** (1) Stop returning `html` and update three test assertions (S). (2) Read Outlook in batches like Gmail (M). (3) Asking Graph for text bodies changes what the classifier sees, so treat it as a behaviour change, not an optimisation.

#### The deferred email-read question ([PERF-9](reports/performance.md#perf-9-re-evaluation-of-the-deferred-emailstoarray-item-measured) (u)): decision is to leave the reads alone

The earlier question was whether the repeated `emails.toArray()` reads should be replaced by something cheaper. The reviewer measured the alternatives in Chrome ([PERF-9](reports/performance.md#perf-9-re-evaluation-of-the-deferred-emailstoarray-item-measured) (u), measured by the reviewer, not independently re-run). Index counts, compound-range scans and `keys()` were no faster than `toArray()`. A `where("applicationId").above(0)` read is about twice as fast with a realistic mix of stub rows, but 25% slower in the worst case, and cannot serve the badge or banner. A single read costs 70 to 200 ms, which is fine. The real cost is how often it runs. **Decision: fix [PERF-1](reports/performance.md#perf-1-every-sync-write-re-runs-three-or-more-full-table-emailstoarray-livequeries-so-sync-runs-about-60-to-90-times-slower-and-the-ui-thread-is-saturated) and leave the reads as they are.** Optionally use `where("applicationId").above(0)` in `listApplications` and `sankey` if stub rows dominate.

permissions:
